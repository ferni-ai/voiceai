# Ferni architecture: the map

Start here to find where code lives. How work ships is in [AGENTS.md](AGENTS.md); each
folder's own `CLAUDE.md` has the details. The layer table at the bottom is generated from
[architecture-layers.ts](apps/cli/src/commands/quality/architecture-layers.ts), the map
`pnpm quality:arch` enforces, so it can't drift from the gate.

## Entry points

| Path | What starts there |
|---|---|
| [src/agent.ts](src/agent.ts) | The voice agent worker (LiveKit). `pnpm dev` runs it |
| [src/startup.ts](src/startup.ts) | Shared bootstrap: memory system, persistence, services, schedulers |
| [src/servers/api/index.ts](src/servers/api/index.ts) | The UI/API server: web routes, webhooks, `/api/jobs/*` for Cloud Scheduler |
| [apps/web/](apps/web/CLAUDE.md) | The web app (Vite), entry `apps/web/src/index.ts` |
| [apps/cli/](apps/cli/CLAUDE.md) | The `ferni` CLI and the quality gates (`apps/cli/src/commands/quality/`) |

## Data stores

- **Firestore**, project `johnb-2025`: `(default)` is prod, `ferni-dev` is dev
  (`FIRESTORE_DATABASE`). Almost all state lives here; adapters are in L1 below.
- **BigQuery** `ferni_events`: product and per-turn analytics rows, written by
  `src/services/analytics/bq-events.ts`, off unless `BQ_EVENTS` is on.
- **Spanner graph** (`ferni-memory` / `knowledge_graph`): the memory graph in
  `src/memory/spanner-graph/`. Dev skips its writes unless `GRAPH_WRITES_ON_DEV_DB` is on.
- **Redis**, only when `REDIS_URL` or `REDIS_HOST` is set (rate limits, cache).
- **Cloud Storage** for uploads and synthesized outreach audio.

## Deploy surfaces

Full table and rollbacks: [docs/runbooks/deploy.md](docs/runbooks/deploy.md).

- Voice agent: LiveKit Cloud (`livekit.toml` dev, `livekit.prod-cloud.toml` prod), by hand.
- UI/API server: Cloud Run `john-bogle-ui`, from `main` by GitHub Actions.
- Web app and website: Firebase Hosting, from `main`.
- Scheduled jobs: Cloud Scheduler, defined in `infra/cloud-scheduler-*.yaml`.

## Where to add things

| To add | Do this |
|---|---|
| A tool | A folder in `src/tools/domains/<domain>/` whose `index.ts` exports its definitions. Read [src/tools/CLAUDE.md](src/tools/CLAUDE.md) |
| A persona | A bundle in `src/personas/bundles/<id>/` with `persona.manifest.json`. Read [src/personas/bundles/CLAUDE.md](src/personas/bundles/CLAUDE.md) |
| A flag | `pnpm flags:new NAME --default off --owner <area> --kind experiment`; commit only `src/config/flags/NAME.ts` |
| A scheduled job | A handler in `src/api/scheduled-jobs/`, its path in `JOB_PATHS` and the switch in `index.ts`, and a job in `infra/cloud-scheduler-*.yaml` |
| A log marker the call miner reads | A row in `scripts/autonomy/log-markers.json` (its test pins the emitting file and count) |

## Planned, not done yet

Decided on 2026-10-31; until each lands, the code and the table below show today's state.

- Outreach (`services/outreach/`, L4 today) will become its own L3 context, the 11th.
- `agents/personas/` will be renamed `turn-path/`.
- The target users collection will be a new `ferni_users`; the existing `users/{userId}` stays as it is.
- The Bogle names (for example the `john-bogle-ui` service) will be renamed; the GCP project
  id `johnb-2025` keeps its name.

## Layers

Dependencies point inward: L5 → L4 → L3 → L2, and L1 adapters implement L2/L3 ports. An L3
context reaches another only through its `index.ts`. Keys are path prefixes and the longest
wins, so `agents/` is L4 while `agents/model-provider/` is L1. Moving a folder? Change its
entry in `architecture-layers.ts`, then run `pnpm docs:map`.
